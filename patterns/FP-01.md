# FP-01 — Stale-Promoted-as-Fresh

| field | value |
|-------|-------|
| id | FP-01 |
| kind | semantic |
| name | Stale promoted as fresh |
| targetFunction | get |

## What goes wrong

When a key lives in `#oldCache`, `get()` checks whether the item has expired before promoting it back to `#cache` via `#moveToRecent`. If that expiry guard is bypassed or inverted, an expired item is unconditionally moved into the hot cache with its original expiry timestamp. The item is then served as live data on every subsequent read until the next full cache rotation discards it.

## Why it hurts in production

Callers receive values that should have been invalidated — for example, stale session data, expired auth tokens, or outdated rate-limit state. The item gains an implicit TTL extension equal to the time until the next rotation, which can be much longer than the original `maxAge`, making the staleness window unpredictable and hard to observe.
