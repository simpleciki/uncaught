# FP-06 — resize() Drops Newest Instead of Oldest

| field | value |
|-------|-------|
| id | FP-06 |
| kind | semantic |
| name | resize() drops newest instead of oldest |
| targetFunction | resize |

## What goes wrong

`resize()` builds an ascending-order array (oldest to newest) from `#entriesAscending()`. To shrink the cache it should keep the tail — `items.slice(removeCount)` — and evict the head. Swapping the slice argument means the head (oldest items) is kept and the tail (newest, most-recently-used items) is discarded, inverting the LRU eviction guarantee.

## Why it hurts in production

A `resize()` call intended to trim a cache down to a working set instead evicts the hottest entries and retains the coldest ones. Applications that resize on memory pressure or configuration reload will find their cache performance collapse: subsequent reads miss on recently used items and hit stale, long-idle entries, increasing downstream load and latency.
