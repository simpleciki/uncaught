# FP-03 — Size Counter Desync on Update

| field | value |
|-------|-------|
| id | FP-03 |
| kind | semantic |
| name | Size counter desync on update |
| targetFunction | set |

## What goes wrong

`set()` has two branches for updating an existing key vs. inserting a new one. The update branch writes directly to `#cache` without going through `#set()`, which is intentional because `#set()` increments `#size` and may trigger a rotation. If the update branch is changed to call `#set()`, the counter increments on every update of an existing key, making `#size` drift above the true count of new insertions.

## Why it hurts in production

The inflated `#size` triggers the rotation threshold prematurely, causing `#oldCache` to be discarded sooner than expected. Live entries that should have survived are evicted, reducing effective cache capacity. High-frequency update workloads (e.g. counters, presence data) suffer the worst degradation: every write accelerates eviction of unrelated items.
