# FP-08 — expiresIn() Wrong Cache Wins

| field | value |
|-------|-------|
| id | FP-08 |
| kind | semantic |
| name | expiresIn() wrong cache wins |
| targetFunction | expiresIn |

## What goes wrong

`expiresIn()` resolves the item with `#cache.get(key) ?? #oldCache.get(key)`: the hot cache wins because it holds the latest expiry. Reversing the lookup order makes `#oldCache` win for any key present in both caches. The hot copy (which may have been re-inserted with a fresh `maxAge`) is ignored, and the stale `#oldCache` copy's expiry is returned instead.

## Why it hurts in production

Callers use the returned value to schedule re-fetches or refresh tokens. When the stale copy's expiry is earlier than the live copy's, callers trigger unnecessary early refreshes, increasing backend traffic. When the stale copy's expiry is later (e.g. after a key was re-inserted with a shorter TTL), callers wait too long to refresh and serve outdated data past the intended deadline.
