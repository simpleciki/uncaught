# FP-04 — Old-Cache Shadow on Iteration

| field | value |
|-------|-------|
| id | FP-04 |
| kind | semantic |
| name | Old-cache shadow on iteration |
| targetFunction | [Symbol.iterator] |

## What goes wrong

When iterating the full cache, `#oldCache` is walked after `#cache`. For any key that exists in both caches (a recently promoted key still has a shadow in `#oldCache` until the next rotation), the iterator must skip the `#oldCache` copy. Removing the `!this.#cache.has(key)` guard causes both copies to be yielded: one from `#cache` and one from `#oldCache`.

## Why it hurts in production

Consumers that spread the iterator into an object, build a Map, or count entries silently receive duplicates. Derived data structures have twice the entries for promoted keys. Algorithms that use the entry count (e.g. `forEach`, `entries()`, downstream pagination) produce off-by-N results, and the error scales with the number of recently promoted keys.
